# 空战沙盒（图4 独立回放页）

> 用户口径（2026-10-02）："**图4 其实应该独立出来作为空战沙盒来展示导弹和敌机飞行过程**"；
> "从功能上我们做的可拖动的交互式沙盒**已经实现了这一功能**了"（⇒ 已有的 `webui_static/viewer3d.*`
> 就是功能底座，**不重写**）。界面口径来源：`.tmp_test/fig3/UI-LAYOUT-REF.md`（输入区布局）与
> `UI-LAYOUT-REF-3D.md` §1–§3（3D 回放 / 悬停框，含两张真实截图）。
>
> 本轮范围 = **回放型**：给定工况把过程完整播出来；**不是**实时改参重算型。

## 1. 与 `viewer3d` 的关系（复用哪一层、为什么不重写）

| 复用（**不重写**） | 出处 | 说明 |
| --- | --- | --- |
| 相机与交互：左键拖动旋转 / 滚轮缩放 / 右键或 Shift 拖动平移 | `viewer3d.js` 的 `applyDrag()` / `applyPan()` / `AZ_PER_PX` / `EL_PER_PX` / `EL_LIMIT` | 与用户给的交互口径逐条一致，由 `global.TRAJ3D` 导出供沙盒调用 |
| 投影与标定：`projectToScreen()` / `M4` / `norm` / `clamp` | 同上（`TRAJ3D`） | 事件标点与悬停框要"贴着世界点"，靠它把世界坐标换算成屏幕像素 |
| 调色：`CHROME` / `hex2rgb` / `mixHex` | 同上 | 亮色 chrome（`#f7f8f9` / `#1f2933` / `1px #d8dce1`）不分叉 |
| 数据层：只读 `results/traj_*.csv|json`，**不解算** | `traj3d.py` | 沙盒在它上面**只加**一个 `build_replay()` |
| 静态白名单 fail-closed | `webui.WEB_STATIC_ASSETS` | 照抄：只放 CSS/JS，页面走自己的路由 |

**不复用**：`viewer3d.js` 的几何模型（它画的是一整条轨迹 + 抽稀点）。沙盒要的是**随时间推进**
的画面（飞过的部分实、未飞的部分淡 + 两个带朝向的实体 + 事件标点 + 悬停取值），几何是**每帧变**的，
所以沙盒自己有一份小的"线段批次"绘制层（程序/缓冲/上传 ~100 行），其余全部走 `TRAJ3D`。
⚠ 这份小绘制层是**有意的小重复**（不引第三方、不重写已验证的 `viewer3d.js`）；若将来要合并，
判据是"`viewer3d` 的 `-k viewer3d` 12 项与沙盒的 `-k sandbox` 都仍然全绿"。

## 4. 悬停信息框（用户 2026-10-02 追加）

行为口径（照参考站实测）：

* **框与回放时刻无关** —— 悬停到哪个点就显示哪个点的值（参考站实测：回放条停在 116.3 s，
  框显示 94.60 s 那一点）；⇒ 取**最近的轨迹采样点**，框**贴着那个屏幕点**显示。
* **导弹与目标两条线都要能悬停**，标题用实体名（导弹名来自 `run.missile`，目标固定写 `目标`）。

字段顺序照抄，右侧是**最终实现与数据来源**。⚠ **仓库第一原则**（用户 2026-10-02 拍板）：
"**有内核完整源码时，先查内核有没有，再决定写不写**"（`AGENTS.md`）—— 内核 `_CF_COLUMNS`
（68 列，含 `kernel-out` 新加的 `mach`/`aoa_deg`/`aoa_eff_deg`）里有的量一律**接出来**，外壳不重造。

| # | 参考站字段 | 实现 | 来源（`kernel` / `derived` / `n/a` / `pending`） |
| --- | --- | --- | --- |
| 1 | 时间(秒) | ✅ `t` | `kernel`：产物 `t_s` |
| 2 | 水平距离(米) | ✅ `sqrt(Δx² + Δz²)`（相对发射点） | `derived`：**内核确实没有**这个量，由内核位置列折出来 |
| 3 | 高度(米) | ✅ `y` | `kernel`：产物 `y_m` |
| 4 | 速度(米/秒) | ✅ 弹 / ✅ 目标 | `kernel`：弹 `speed_m_s`（`v_ms`）、目标 `target_speed_m_s`（目标表 `v_ms`） |
| 5 | 马赫数 | ✅ | `kernel`：内核 `mach`（= `\|air\| / sound(alt)`，**外壳不派生**） |
| 6 | 加速度(米/秒²) | ✅ | `derived`：内核 `accel_x/y/z_m_s2` 在**内核速度方向**上的投影（`v̂` 取 `vx/vy/vz_ms`）；口径见 §9.1 |
| 7 | 到目标的距离(米) | ✅ | `kernel`：产物 `range_m`（弹目斜距）。两张产物表是**同一条时间轴**（`t_s` 逐位相同，判据钉住），目标侧按下标对齐取同一列 |
| 8 | G载荷(G) | ✅ | `kernel`：`trajectory_normal_g`（轨迹法向过载）；另两个（`sf_g` 比力 / `req_g` 指令）进 `extra` 组 —— 三者不是一个量 |
| 9 | 攻角(°) | ✅ | `kernel`：`aoa_deg`（运动学 `∠(nose, 空速)`）＋ `extra` 里的 `aoa_eff_deg`（内核 `aero()` 实际用的 `∠(nose, flow)`，含力臂/角速度项） |
| 10 | 已行驶距离(米) | ✅ | `kernel`：`distance_flown_m`（**不由前端积分**） |

契约里还有一组 **`extra`**（不进参考站那 9 行）：`sf_g`（比力过载）、`req_g`（指令过载）、
`aoa_eff_deg`（内核 `aero()` 口径的攻角）—— 三个都是内核列。

**三种"没有值"要分开渲染**（前端判据钉住）：

| 情况 | 契约里的 `source` | 框里显示 |
| --- | --- | --- |
| 内核列还没进产物 | `pending` | **待接入**（并在左栏"数据来源"列出它缺的是哪个内核列） |
| 这个量对该实体不成立（目标没有体轴/推力/制导） | `n/a` | **不适用** |
| 内核在这一采样点确实没定义（例如 t=0 那一步的过载） | 值是 `null` | **—** |

⚠ 差额实现（`traj3d._axial_accel()` / `_cumulative()` / `_speed_of()`）**只出现在判据里**当对拍照
（§8.4 有三条实测数字），既不进响应也不进框 —— 框里显示的一律是内核值或内核值的投影。

## 5. 内核 65 列 ↔ 我们的产物列（"待接入"清单与计划）

内核输出 schema 是 **65 列**（`vendor/wt-missile/wt_missile.py` 的 `_CF_COLUMNS`，第 2009–2018 行；
⚠ Lead 2026-10-02 实测更正：**不是 60** —— `kernel-out` 分支已经在加 `mach`/`aoa_deg`/`aoa_eff_deg`，
加完 **68 列**，而这三个量的口径已定为"**必须由内核给出，外壳不派生**"），
而我们自己的精简层只往外写了 **8 列**（`solver.trajectory()` 第 343–353 行 12 个键 →
`record.write_traj_track_csv()` 第 249–250 行 8 列）：

| 要的字段 | 内核 65 列里的源头 | 现状与我们打算怎么做 |
| --- | --- | --- |
| 到目标的距离 | `range_m` | ✅ 产物已有 |
| 速度 / 高度 / 时间 | `speed_m_s` / `missile_y_m` / `time_s` | ✅ 产物已有（**弹**侧） |
| 目标速度 | `target_speed_m_s` | 内核有、产物无 ⇒ P6 加列；**在此之前显示"待接入"** |
| **加速度** | `accel_x/y/z_m_s2` | 内核有、产物无 ⇒ P6 加列（框里显示**速度方向上的投影**，口径要写明） |
| **已行驶距离** | `distance_flown_m` | 内核有、产物无 ⇒ P6 加列（**不**用累加弧长顶） |
| **G 载荷** | `trajectory_normal_g`（轨迹法向）/ `specific_force_g`（比力）/ `requested_g`（指令） | 内核有、产物无 ⇒ P6 加列。**三者不是一个量**，接上时必须在文档与框里写明用的是哪一个（初选 `trajectory_normal_g`）；另两个放 `hover.fields` 的 `extra` 组 |
| **攻角** | 列里**没有这个名字**：由 `qx,qy,qz,qw`（姿态）+ `missile_vx/vy/vz_m_s`（速度）算 | 口径：内核 `aero()` 里 `nose = unit(R[:,0])`（第 788 行），但它比的是 `flow = unit(air + R @ [0, lever·ω_z, −lever·ω_y])`（第 793–794 行，**含力臂/角速度项**）。我们给**两个**：`aoa_deg` = 运动学攻角 `∠(nose, 空速)`，`aoa_eff_deg` = 内核那个 `∠(nose, flow)`（Lead 2026-10-02 定：用户要"从内核拿"，所以内核口径必须在），**并在真实轨迹上给出两者的数值差**。 |
| **Mach** | 无直接列：`air_speed_m_s`（**真空速**，不是马赫！）× 声速 | 声速走 **atmosphere.cpp 的大气解**（用户 2026-10-02 拍板）：新建 `src/missile_sim/atmosphere.py`。**判据**：与内核 `_atmosphere(height) -> (rho, sound)`（第 67 行，纯 Python；C 侧 `atmosphere()` 在 1475 行）在若干高度上交叉核对，容差写清。默认工况 `wind = [0,0,0]` ⇒ 真空速 = 地速，但实现仍按 `air_speed_m_s` 口径。 |

⚠ **纪律**：拿不到的字段**不许编**。P3 只显示"待接入"；P6 完全落地后，框里每个数要么来自产物列，
要么来自 `atmosphere.py` 的显式公式（并注明"由高度算出的声速"），没有第三种来源。

## 6. 时间轴 / 镜头 / 参照（照参考站，位置有修正）

* **回放条在主视图顶部**（不在左栏）：左起 **↺ 重播 / ⏸ 暂停 / ⏭ 单步**，右侧**贯通整宽**的进度条 +
  末端 `已播放 / 总时长`（参考站实测 `116.3s / 116.3s`）。这条**修正**了 `UI-LAYOUT-REF.md`
  里"时间轴放左栏"的推断。
* **倍速在左栏**（`0.25× / 0.5× / 1× / 2× / 4×`，默认 `1×`）；**镜头**在左栏：跟随导弹 / 跟随敌机 / 自由；
  另有"显示事件标签 / 显示地面网格"开关。左栏**可折叠**且状态记 `localStorage`。
* **图例在主视图右上角**，用**线型**区分双方（不只靠颜色）：导弹 = **粗实线**、目标 = **虚线**。
  ⚠ 颜色仍走我们的 `figures` 配色（`TRAJ_*`，开机前/后两段同色相派生），**不写死字面量**。
* **三轴刻度带 `k` 后缀**，轴名带方向与单位：`前向距离 - X（米）` / `高度 - Y（米）` /
  `侧向距离 - Z（米）`。⚠ 参考站写的是 `高度（米向距离 - Z）`（把"高度"和"Z"混在一句里，自相矛盾）；
  我们按实际坐标轴（`y` = 高度、`z` = 侧向）命名 —— **这是有意的偏差**。
* **双方实体**：带朝向的**线框**（机身轴 + 翼/尾面），朝向取自轨迹：导弹用逐点速度方向（航向 + 俯仰），
  目标用 `segments` 的 `heading0/1_deg` 内插（解析值，来自航向指令），**都不是常量**。
  ⚠ 线宽固定 1 px（WebGL 的 `lineWidth` 在多数实现里被忽略）—— 所以"看得见"靠的是
  **实体线框 + 事件标签 + 已飞/未飞两段深浅对比**，不靠加粗。
* **镜头**：跟随 = 把相机中心移到该实体当前点上（保持用户当前的方位/俯仰/距离），自由 = 现状。
* **自适应取景**：初始视距先按包围球算（查看器那套 ×0.72），再按**真实点集**迭代放大，
  直到两条轨迹的所有采样点都落在视口内 —— 只按包围球会裁掉轨迹两端（沙盒里还有一大片地面网格，
  球半径被网格带偏）。网格被裁无所谓，**交战双方必须都在画面里**。
* **DOM id 命名规则**：沙盒页自己的元素一律 `sb` 前缀（`sbScene`/`sbHover`/…）。
  理由：`viewer3d.js` 的 `boot()` 会在 `window` 里自己跑一遍并在缺 `#cv` 时静默退出 ——
  只要沙盒页**不出现它的那批 id**（`cv`/`err`/`btnOpen`/`legend`/…），两页共用一个脚本就互不打扰。
  判据里有一条专门钉这个（缺 `#cv` 且不出现它的 id）。
* **调试入口**（⚠ **不是正式功能**，只为取证/复查而留；判据不看它们）：`?t=<秒>` 定位到某一时刻、
  `?paused=1` 进来先停、`?follow=<key>` 指定镜头、`?az=`/`?el=` 给相机初值、
  `?hover=<实体>:<下标>` 把悬停框钉在某个采样点上（截图可复现）、`?debug=1` 把
  `t/playing/speed/follow/hover/canvas 尺寸/dist` 写进 `document.title`（无需新 DOM，
  用可访问性树就能读到回放状态）。正式入口只有 `?job=` / `?points=`。

  行值有"列数不匹配就 raise"的自检，判据也**分别**断言两张表的列集合。
* 内核列以合并后的 `_CF_COLUMNS` 为准：少哪一列，对应字段就**保持 `pending`** 并报 Lead，
  不许拿别的列顶（`_downgrade_spec()` 就是这条规则的实现）。
* `docs/SOLVER-API.md` §3.1 归 Lead（我不改）：本轮对拍照的数字已在 §8.4，Lead 直接誊。

### 9.8 与草案的四处差异（事后补记）

1. **多加了 3 列**：`vx_ms / vy_ms / vz_ms`（草案只有 19 列 ⇒ 实际 **22 列**）。理由：加速度投影
   需要 `v̂`，弹的朝向也用它；没有这三列，"投影"就只能拿位置差分当方向，反而不是内核口径了。
2. **`derived` 也要按列降级**：草案只降 `kernel` 意图；实际 `accel_ms2` 是"我们投影、但输入是内核列"，
   老产物缺输入列时它必须一起降成 `pending`（否则契约说"算得出来"而 `series` 里没有这一列）。
3. **"没有值"分成三种**：`待接入`（缺列）/ `不适用`（该实体没有这个量）/ `—`（内核在该点没定义）。
   草案只有前两种，第三种是接上真产物才暴露的（t=0 那一步的 `trajectory_normal_g` 是 `null`）。
4. **目标侧 `range_m` 的去处**：它取的是**弹表**那一列（两张表同一条时间轴），所以
   `FIELD_COLUMNS` 里特意标出"去哪张表查列"，不能默认查自己那张表。
