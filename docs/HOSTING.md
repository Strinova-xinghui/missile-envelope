# 公网托管：差距、架构取舍与 AGPL 下的合作结构

> 起点：用户 2026-10-04 的目标是"像 StatShark 一样放到网站上让别人用，但不想别人拿了后端闭源卖同款"，
> 因此许可定为 **AGPL-3.0-only**（见 `docs/OSS-LICENSE.md`），并考虑与 `sensorwhale.com` 合作托管。
> 本文把"上公网"拆成可执行阶段，并写清**合作时 AGPL 会怎么约束对方**。
> 事实来源：`docs/REFERENCE-NEOTHUNDERISM.md`（对拍对象，2026-10-02）与
> `docs/REFERENCE-SENSORWHALE.md`（候选托管方，2026-10-04 本轮新增）。决策记录见 `NOTES.md`。

## 0. 一句话

**算法、三张图、前端、许可都已就绪**（这是最难的一半）；缺的是整层"**公网多租户服务**"。
建议顺序：**先做零算力的"静态只读站" + 两条合规前置**，再按阶段开放交互。

## 2.1 候选托管方的两条硬约束（2026-10-04 独立复核新增）

1. **架构级不匹配**：它的算力在**浏览器**（加密 WASM），我们是**服务端 Python 重 CPU 任务**
   （fast 档 1824 点 ≈ 0.27 min）。共用它那台**腾讯云上海单机**（无 CDN、无 `Cache-Control`）= 我们的请求与它 717 个用户抢同一台机器。
2. **没有合规兜底**：个人备案 + 站内**无条款/隐私政策** + 用户在站内留下 Gaijin 凭据（bundle 内有
   `testGaijinLogin(email,password)` 与"绝不上传"的矛盾措辞）⇒ 与之联署会把我们的声誉一起绑上去。
3. 附带一条**反面教材**：它的"加密内核"（`SWEN` 容器 + 混淆入口）配上**无鉴权明文的 `/api/engine-key`**，
   等于把引擎送人 —— **加密不等于保护**。我们的杠杆是 AGPL + 校准/数据/体验，不是把引擎藏起来。
4. 站内**没有托管第三方工具的机制**（无插件体系、无 API key、无开放文档）⇒ "合作托管"没有现成接口，
   实质是"两个同赛道作者合并"，一切要从零约定。

## 3. 我们上公网的三种架构

| | **A 客户端算核（WASM）** | **B 服务端 Python（现状直接上云）** | **C 混合** |
| --- | --- | --- | --- |
| 服务器成本 | ≈ 0（只发静态资源） | 高（每次请求 539~1632 个工况） | 低（重活仍可下沉） |
| AGPL 触发面 | 只有**分发**（发布源码即可，§4/§5） | **§13 网络交互**：对外提供服务者必须向使用者提供对应源码 | 同 A |
| 数据合规 | 必须把（部分）参数下发到客户端，或改用**公开镜像运行时拉取** | 数据留在服务器（现行最干净） | 中 |
| 工作量 | **大**：C 内核 → WASM（emscripten/WASI）+ 壳/网格/出图逻辑移植 + 数据管线 | **小**：反代 + 队列 + 配额 + 容器化（内核已支持 Linux） | 中 |
| 适合何时 | 长期目标（用户量上来之后） | **阶段 1 的现实选择** | 阶段 2/3 演进 |

> 注：C 内核是 C11、无第三方依赖，编到 WASM 是**可验证的 spike**（先证明"能编过 + 数值一致"再谈产品化）；
> 但 §5 的 Python 侧（`bg`/`pool`/`grid`/`figures`）要移植，这才是大头。

## 4. AGPL 下的合作结构（关键，谈之前先定）

1. **对方原样托管我们的公开版本**（独立子域/独立应用，不改代码）⇒ 对方的义务只有"向上站用户提供源码"，
   由一个指向公开仓的链接即满足 ⇒ **最省事、最干净的合法合作**。
2. **对方要把我们的引擎集成进他们自己的（闭源/加密）产品** ⇒ 那是"修改版 + 通过网络提供"，
   第三方**必须公开其对应源码**；**除非**我们以版权人身份**另行给出一份书面例外/商业授权**
   （必须写清：范围、是否排他、可否撤销、能否二次分发、期限）。
3. **一旦接受外部贡献**（含对方的代码提交），要保持"可双许可"的自由就必须走 **CLA**
   （或至少 DCO + 明确的授权条款）——目前仓库还没收任何外部贡献，这个自由还在我们手上。
4. **数据风险归属要写进协议**：谁在用 Gaijin 数据、谁承担后果。参考站"运行时从公开镜像拉取"的做法
   比"把数据打进包"干净得多，建议合作时也走这条。
5. 记住 AGPL 的**边界**：它只保证"别人不能闭源卖"，**不阻止**合规竞争者（公开源码后自建）。
   真正的护城河是：数据 + 校准 + 体验 + 算力预算 + 品牌，以及**最新校准留在我方服务端**
   （版权人对自己的实例可以私有改进；一旦收了无 CLA 的外部贡献，这条自由就受损）。

## 5. 与 `sensorwhale.com` 合作的尽调清单（谈之前逐条问）

> **完整 31 条（A–I 组，每条带"为什么重要/答错会怎样"）见 `docs/REFERENCE-SENSORWHALE.md` §7；
> 下面只是提要。C 组（AGPL 与授权）是硬前提：任一条不接受，其余都不必谈。**

**成本与权责**

* 域名 / 证书 / 服务器 / 带宽谁出？成本上限多少？超限如何降级（限流？只读模式？）——*答不清就会变成"我出算力、他收流量"。*
* 算力按谁的额度走？被刷爆（恶意刷 539 工况）谁背锅、谁停服？

**AGPL 与代码**

* 他们是否接受"若托管我方**修改版**，必须向上站用户提供他们的对应源码"？
  若不接受 ⇒ 唯一合法路径是我方给一份**书面例外授权**，此时要定：排他/非排他、可否撤销、范围（仅托管？可否二次分发？）、期限。
* 他们现有引擎是**加密 WASM**（见 `REFERENCE-SENSORWHALE.md` §2）——这与 AGPL 的"源码可得"存在**结构性张力**，
  必须先说清是"两个独立应用并存"还是"引擎级集成"。

**品牌与数据**

* 站点署名 / 谁的商标 / 谁的域名？能否打"官方"字样？
* 用户数据与计算结果（图、CSV、JSON）**权利归谁**？能否带走？
* 数据来源用哪条链（他们现有的公开镜像？我方自备？），风险谁承担？

**排他与退出**

* 是否要求独家？我方能否同时自建站点？
* 停止合作后：产物、域名、用户、日志谁能带走？我方站点能否独立跑起来（可迁移性）？

**交付与边界**

* 他们能提供什么（托管 / 推广 / 数据 / 运维 / 备案主体）？我方要给什么（代码 / 授权 / 品牌）？
* 他们的**备案主体是个人（李海锐）**（`REFERENCE-SENSORWHALE.md` §1）——大陆个人备案一般不得用于**经营性活动**；
  若要商业化托管/收费，这条必须先弄清（本条是合规提示，不是法律意见）。

### 6.0.1 GitHub Pages 打通（2026-10-05）

**结论：只把"构建好的站点"推到一个孤儿 `gh-pages` 分支 —— 不要推源码仓。**

为什么不能推源码仓：`vendor/wt-missile/inputs/**`（War Thunder 的 168 份 blk，权利归 Gaijin）虽然被
`.gitignore` 挡住，但**历史里仍有它的对象**（`git log --all -- vendor/wt-missile/inputs/*` 有命中）⇒
推上去等于公开分发游戏数据。源码仓要公开，必须先走"干净历史"那条路线（`docs/OPENSOURCE-READINESS.md` §4.3）。

做法（已在本机备好，`git push` 一步即可上线）：

```powershell
python scripts\build_static_site.py --app --out build\site-app     # 1) 组装（含 .nojekyll）
cd E:\导弹包线图-ghpages                                            # 2) 发布 worktree（孤儿分支 gh-pages）
Remove-Item * -Recurse -Force -Exclude .git,.gitattributes; Copy-Item E:\导弹包线图-release\build\site-app\* . -Recurse -Force
git add -A; git commit -m "重出站点"; Pop-Location
git remote add origin https://github.com/<账号>/<仓库>.git            # 3) 一次
git push -u origin gh-pages                                         # 4) 推送（认证由你完成）
```

然后在 GitHub：**Settings → Pages → Source = Deploy from a branch → `gh-pages` / `(root)`**。
站点地址 = `https://<账号>.github.io/<仓库>/`（**项目页子路径** —— 我们全部用相对路径，已在子目录形态实测）。

* 该分支**零历史**：不含源码、不含游戏数据、不含仓库其余 800 MB ⇒ 可以安全公开。
* `.nojekyll` 关掉 Jekyll；`.gitattributes` 钉 `* -text`，保证发布字节 = 构建字节。
* 重新发布就是上面 1→4（改了站点内容后，记得先在源码侧提交，再重出站点）。
* ⚠ **AGPL §13 待办**：源码仓公开后，用 `--source-url https://github.com/<账号>/<仓库>` 重新组装一次，
  让页面带上源码入口（现在未给该参数 ⇒ 页面里没有源码链接，符合"不写占位 URL"的纪律，但 §13 要求最终要有）。
