## 2. 图3 画什么（主方案：纯俯视 + 侧视小窗）

### 2.1 坐标系与航向（内核口径，必须照抄）

内核 `Target.velocity()`：**`heading 0 = +x`、`90 = +z`、`180 = −x`**。本题设里：

* 载机在 x 正侧，敌机从 +x 迎头飞向 −x（`start_heading_deg = 180`）；
* crank 段 = 110°（从迎头转 70°，`cw` 方向）；
* 39 段（正侧方）= **90°** ⇒ 俯视图里是一条**平行于 z 轴**的直线，与发射轴垂直；
* 所以"110° 的 crank 段比 39 段偏 20°"这件事，只有**等比例坐标**（`set_aspect("equal")`）
  才看得出来 —— 这是俯视面板的唯一硬性绘图要求。

### 2.2 主面板（俯视 x–z）

导弹航迹（细虚线）+ 目标航迹（**分段着色**）+ 5 类节点 + 命中点/脱靶标注 +
"我方/载机"方向标注。x 范围按弹道自适应，z 范围按目标航迹自适应并留边。

### 2.3 副面板（高度–时间）—— 一物三用

用户说"标注或开侧式小窗描述清楚"。推荐副面板画 **高度–时间曲线**（目标 + 导弹），
与主面板**共用同一批节点时刻**，两幅图的节点在纸面上**竖直对齐**：

1. 让**高度方向**的东西可见（**震荡**、爬升/高抛、俯冲）——俯视图天然丢这一维；
2. 让"节点在时间上的先后与疏密"可读（crank 段多长、39 段多长、t_beam 落在哪）；
3. 脱靶/`lifetime` 时曲线会一直延伸，读者一眼看出"39 段拖了很久还是没接上"。

可选的第三种表达（若用户更喜欢几何对应）：侧视 **x–y 纵剖面**。两条都做的话就是三面板，
**默认只出"俯视 + 高度–时间"两面板**，x–y 剖面留作开关。

### 2.4 放大 inset

"开机 → 转 39"那一段只有 1~2 s、角差只有 20°，在 50 km 量级的俯视图里看不出来。
主面板角落放一个 inset 圈出该段并放大（画分段色与 t_beam 节点）。

### 2.5 ⚠ 震荡的可见性（图注必须写清）

用户原话是"以一个**固定频率和振幅轨迹上下震荡**飞行"。若"上下"指**高度方向**，
俯视图里**完全看不到**（会是一条平滑的 39 段直线）—— 这正是副面板存在的理由。
图注里要显式写：`震荡 ±A° / f Hz（高度方向，见下方高度–时间图）`。
若其实指**水平面内左右摆动**，则主面板直接可见，副面板照常画高度（不冲突，两条都成立）。

## 3. 节点与分段（本图的定义）

### 3.1 关键节点（用户点名的 5 类）

| 节点 | 由什么决定 | 图上怎么画 |
| --- | --- | --- |
| **发射**（隐含起点） | `t = 0`，双方初始位置 | 导弹航迹起点 + "我方"方向标注 |
| **开始转入 crank** | `t_crank`（用户可调） | 目标航迹上实心圆点 + 文字 `t=..s` |
| **crank 段** | 转弯段 + 110° 保持段（见 3.2） | 一整段**独立颜色** |
| **导引头开机** | 首次 `range ≤ lockDistance`（**一遍法**反求，§8.2/§8.8.4） | 导弹航迹上空心大圆 **+ 一条连到目标当时位置的细线**，标 `开机 · R = 16.0 km`（比单个点信息量大得多） |
| **开始由 crank 转入 39** | **`t_beam + react_delay_s`**（开机时刻 + 人的反应时间，默认 1.0 s） | 目标航迹上实心圆点（与"开机"点**分开**，两点之间那段时间目标仍在原航向上） |
| **39 段** | 转入 39 的转弯段 + 90° 保持段 | 一整段**独立颜色**，直到命中/结束 |
| **命中 / 结束** | `shot.hit` / `t_hit` / `lifetime` | 命中点星标；脱靶则标最近点 + 脱靶量 |

### 3.2 分段表（颜色建议，PNG/PDF/SVG 通用，不依赖字体）

分段**直接由 `PathSchedule.table()` 那张分段常值 ω 表折出**，不另做时间算术
（避免出现第二套口径，也是 §8.3"腿重叠"坑的结构性防线）：

| # | 段 | 时间区间 | 航向 | 颜色键 |
| --- | --- | --- | --- | --- |
| 1 | 直飞（迎头） | `[0, t_crank)` | 180° | `grey` |
| 2 | 转入 crank（转弯） | `[t_crank, t_crank+Δ1)` | 180° → 110° | `orange` |
| 3 | crank 保持 | `[t_crank+Δ1, t_react)` | 110° | `red` |
| 4 | 转入 39（转弯） | `[t_react, t_react+Δ2)` | 110° → 90° | `teal` |
| 5 | 39 保持 | `[t_react+Δ2, 结束)` | 90° | `blue` |
| — | 导弹航迹 | `[0, t_hit / 结束]` | — | 深灰细虚线 + 命中点 |

其中 **`t_react = t_beam + react_delay_s`**（"看到 RWR 告警才开始转"，默认延迟 1.0 s）。
`Δ1 = radians(crank_deg)/(g·g0/v)`（9G、70° ⇒ 4.15 s）、`Δ2 = radians(20°)/ω2`（⇒ 1.19 s）。

**⚠ 延迟期间目标并没有"停着等"**：它仍在原航向上飞 —— 也就是说第 1 段直飞（或第 3 段
crank 保持）会**延长** `react_delay_s` 秒。这正是"开机"与"开始转 39"两个节点要分开标的原因。

⚠ **"没转完"在本图里天然可见**：若 `t_react < t_crank + Δ1`，两条指令在**同一时刻**下达，
后一条截断前一条（`flightpath` 的既定语义），目标从 180° **一条弧**直接转到 90°，
**第 3 段（110° 平台）整段消失** —— 这正是"实战中没能完成 39 干扰 ⇒ 被击落"的可视化。
图例里单列这一条（如"crank 未转完（被压成一条弧）"）。

⚠ **开机早于 crank 时的分支（用户 2026-09-30 定稿）**：原话"开机早于 crank 则同样给与延迟，
因为等于是没准备预规避直接开始39"。即 `t_react < t_crank` 时**丢弃 crank 腿**，
腿表只有一条 `39 @ t_react`（180° → 90° 一次转完），延迟照给。
**这条规则现在的代码不对** —— 详见 §5 P1 与 §8 第 12 条。

### 3.3 反应延迟的实测效应（2026-09-30 新测，图3 要能看出来）

| 场景 | 结论 |
| --- | --- |
| 远离边界（PL-12/16 km/t_crank=8/9G，本来就命中） | 延迟是**二阶**：t_hit 只早约 **0.38 s / 秒延迟**（0 s 69.554 → 1 s 69.172 → 3 s 68.418），全部仍命中 |
| 边界附近（脱靶格：10/12/14G） | 延迟是**一阶**：脱靶量随延迟**线性变小**，约 **−78 m / 秒**（10G：229.6→190.1→151.0→112.1→73.8 m） |
| 11 型里脱靶的五型（各用自己 `lockDistance`，延迟 0→1.0 s） | 落在同一条线上：R-77-1 −78.8 / MICA −72.3 / R-Darter −80.5 / R-77 −82.9 / Derby −74.0 m |

**机理（别把方向写反）**：延迟期间目标仍在 110° 上飞，而 110° 的 x 分量是 `cos110° = −0.342`
⇒ **仍在向导弹靠近 103 m/s**。所以"多飞 282 m 侧向"被"多逼近 103 m"抵掉一部分，
**净效应是帮了导弹**。⇒ "看到告警才转"对目标是个真实的代价，不是模型噪声。

**完整的实测表与口径**见 `docs/MANEUVER-TARGETS.md` §8.9。图3 的图注里建议给出
`react_delay_s` 的值，并在高度–时间副面板上把"开机 → 转 39"那段延迟画出来（它是可读的一段）。

## 4. 数据契约（"输入/输出 API 化"的落点）

新增一层**纯数据**中间层，供出图、CSV、JSON 三方共用（沿用仓库风格：dataclass + `as_dict()`，
出图模块只吃这一种输入）：

```python
@dataclass(frozen=True)
class Segment:            # 目标航迹的一段
    t0_s: float; t1_s: float
    kind: str             # straight | turn | hold
    label: str            # 直飞 / 转入crank / crank保持 / 转入39 / 39保持
    heading_deg: float
    color_key: str

@dataclass(frozen=True)
class TrajMark:           # 一个节点
    name: str             # launch | crank_start | crank_done | seeker_on | beam_start | beam_done | end
    t_s: float
    note: str             # 图上的文字，如 "开机 · R=16.0 km"

@dataclass(frozen=True)
class TrajRun:
    scene: Scene                    # 输入工况（含 maneuvers）
    schedule: PathSchedule          # 目标航向指令（模型层对象）
    shot: Shot                      # 求解器输出（hit / t_hit / miss_m / event / backend）
    rows: list                      # 求解器原始输出（时间栅格；画图与查表都靠它）
    segments: list[Segment]
    marks: list[TrajMark]
    anchor: dict                    # lock_distance_m / mode / t_beam_s / completed(bool) / heading_at_beam_deg
    missile: str                    # 弹池短名（决定 lockDistance 与 (β, γ)）
    beta: float; gamma: float
```

落盘（沿用 `record.py`）：`results/traj_<tag>.json`（manifest + 全部分段/节点）+
`results/traj_<tag>_target.csv` / `_missile.csv`（航迹点）。**图里每个节点时刻都能在 CSV 里查到**，
这是"可复核"的验收条件。

## 6. 输入阶段的 3D 预览（为什么它可行、怎么低成本做）

用户："开始解算前用户输入的时候也有 3D 动画直观展示，我觉得这样用户是能拿捏准的。"

**关键洞察：目标航迹是纯运动学，不需要求解器。** `PathSchedule.samples()` 只依赖
（速度、起始航向、`t_crank`、`crank_deg`、转向过载、`beam_deg`、震荡）—— 毫秒级。
所以"改一个参数 → 立刻看到 3D 轨迹"完全做得到，解算那几十秒留给后面的正式图。

* **画什么**：目标航迹 3D 曲线 + 分段着色 + 节点 + 指令航向时间线（可选叠加导弹航迹，
  但那要等解算完）；
* **3D 怎么来**：`mpl_toolkits.mplot3d`（matplotlib 自带，**无新依赖**）；
* **"动画"怎么做而不破坏离线约束**：服务端按方位角预渲染 N 帧 → 前端一个 `<img>` 定时轮播
  （纯标准库，不引外部 JS、不联网）。现有 WebUI 是"纯标准库表单 + 后台任务 + 进度轮询"，
  分发包要"双击即用"，这条约束**不能破**；
* **价值**：用户能在解算前看清"70° 是朝哪边转、crank 段多长、震荡在哪个平面里摆"，
  这正是"拿捏得准"的关键；也天然回答 §2.5 那个"震荡在哪个方向"的问题 —— 图上直接看得见。

## 7. 备用方案：可交互 3D（鼠标拖动换视角）

用户："已经做成 3D 了应该有用鼠标拖动改变视角的可行性，但这需要交互式网页，记为备用方案。"

* **为什么诱人**：数据本来就是 3D 的（含高度），俯视图天然丢一维；
* **形态**：本机 WebUI 里嵌一个可拖动旋转的 3D 视图；
* **成本与约束**：现有 WebUI 是纯标准库 + 离线分发包（双击即用、不联网）。要上 Three.js
  之类必须**单文件内联**、不允许 CDN；或者服务端按需渲染（拖一次请求一帧，延迟与画质一般）。
  ⇒ 所以记为备用，**主方案不依赖它**；
* **低成本中间态（可以先做，不引任何前端依赖）**：服务端渲染**多角度拼图**（如 4 个方位角
  一张图）或"转一圈"帧序列 —— 与 §6 的动画是同一套机制；
* **触发条件**：主方案（俯视 + 高度–时间 + 放大 inset + 输入阶段 3D 预览）落地后，
  若仍觉得视角不够用再上。

## 8. 已知坑（实施时逐条对照）

1. ~~加面板必然改现有图2 的字节~~ → **独立成图3 后此坑消失**（这正是采纳独立的收益）。
2. **`rows` 没有 `x_m`**，是 `missile_x_m`；速度列是 `speed_m_s` 而不是 `missile_speed_m_s`。
3. **`t_hit` 可能不在时间栅格上**（事件时间），画命中点要单独取该时刻位置，不能只截最近栅格点。
4. **脱靶 / `lifetime` 的轨迹会一直画到 `duration_s`**（39 段可能几十秒），必须裁范围并说明。
5. **等比例不能省**：不等比例时 110° 与 90° 看起来一样，图的结论就错了。
6. **震荡的可见性**（§2.5）：俯视图看不到高度方向震荡，`高度–时间` 副面板是它的落点；
   图注必须写明，否则读者会以为震荡没生效。
7. **"没转完"不要当成错误输入**：出图要画成一条弧并在图例里解释它 = "没做成 39 干扰 ⇒ 被击落"。
8. **开机时刻的锚点必须用同一枚弹反求**（§8.8.4：弱弹差 1.7 s，边界附近会翻转命中）。
9. **不要把预跑结果当最终结果**返回（两个 Scene 的缓存条目要分清）。
10. **题头/脚注是手工锚定的**（`add_bg_header` / `xlabel_bottom_fig`）：图3 是新画布，
    脚注的 `y0` 要按自己的版面另算，不要照抄图2 的数值。
11. **输入阶段的预览绝不能"顺手跑一次求解器"**：那会把"改一个参数即时看到"变成
    "等几十秒"，整个体验就没了（§6）。
12. ⚠ **`crank_beam()` 现在的边界规则是旧的**（`t_beam = max(t_beam, t_crank)`，且没有延迟参数），
    与用户 2026-09-30 定稿的规则（§3.2）**不一致** ⇒ 必须在 P1 改掉并改对应测试。
    别照抄现有实现的语义去写图3。
13. ⚠ **别把"延迟帮谁"写反**：延迟期间目标在 110° 上仍有 `cos110° = −0.342` 的接近分量，
    所以**延迟帮导弹**（每 1 s 吃掉约 78 m 脱靶余量，§3.3）。图注里若要说"反应慢更危险"，
    方向是对的；但不要写成"延迟让目标更容易逃掉"。
14. **两个节点必须分开标**：`react_delay_s` 默认为 1.0 s，所以"开机"与"开始转 39"通常**不重合**；
    图上要各画一个点，中间那段时间目标还在原航向（图注写明）。
